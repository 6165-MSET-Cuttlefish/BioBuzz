- **deploySloth** (hot reload): everything else. It returns before the load lands: wait for the `Processed Sloth Load` toast (DS, RC screen or logcat; it took 9-9.5 s on 2026-11-14, so without one wait 12) before redeploying or pressing INIT, or the app restarts or the INIT never runs (`docs/hub-bench-findings.md`).
- The hub's clock reads 31 Dec 1969 after boot (seen 2026-11-14) until a DS connects or a browser opens `http://192.168.43.1:8080` (that part unchecked). A load pushed while it reads earlier than the APK's install time is deleted at the next app restart (logcat `removing outdated sloth load`) and the installed APK's code runs: connect the DS before deploySloth (`docs/toolchain-findings.md`).
- Verify with `./gradlew :TeamCode:compileDebugJavaWithJavac` (`:TeamCode:assembleDebug` for the APK); after an AGP or Gradle bump, also `:TeamCode:assembleSloth`, which hooks AGP's dex task by name. Unit tests (no hardware): `./gradlew :TeamCode:testDebugUnitTest`.

- After a full install that adds, renames or deletes a `res/xml` file, re-activate the hub's hardware config on the DS: the hub stores it by resource ID, which shifts, so it can load another config's devices under the old name (`docs/toolchain-findings.md`).

- A hub's logcat has its Wi-Fi name and password from every app start, and its ports and adb take no credential: strip those lines before quoting a log in `docs/` or anywhere public. Pedro Pathing 3:

- `Pose.heading()` is in [0, 2π).
- `BezierCurve.length()` can under-report an S-curve down to its chord, and `parameter()` and `remainingDistance()` inherit it: never use them for timeouts or route costs. `PathCommands.followUntilRemaining` and `remainingBelow` fire early on such curves.
- `follow`/`followThrough` brake at the end; legs keep speed through a join only as segments of one `Paths.path(...)` or via a `followUntilRemaining` handover before braking.
- A heading jump over 11.25° at a join gives turning priority over driving; `architecture/auto/PathHeadings` gives headings that avoid it.
- A lambda passed to `path.heading(...)` gets path completion (per piece inside `piecewise`), not the curve's `t`: wrap it in `Interpolator.geometric(...)` for `t`. `reverse()` drops `geometric`, so `reverseTangent()` and `facingPoint(...).reverse()` are wrong on curves: use `PathHeadings` (`backwardTangent` to drive one backwards).
- Pedro ignores a NaN or infinite drive power and leaves each motor at its last power, so the robot drives on: check `Double.isFinite` before a value reaches a path or the follower (`docs/pedro-findings.md`).

## Framework layout

`initializeGameModules()` runs inside `Robot`'s constructor, before the subclass's field initializers and constructor body: it sees subclass fields unset, and an initializer on a field it assigns (even `= null`) overwrites it.

**Poses and alliance**

- Author poses for RED with `FieldPose.forAlliance(x, y, heading)` and take path headings from those poses: a raw radian passed to a path (e.g. `linear(...)`) isn't mapped to BLUE.
- `Robot` puts the follower at a placeholder pose every INIT: call `robot.follower.setPose(start)` in `initialize()` before building paths. Odometry runs from INIT, so put the robot on its start before INIT and don't move it after.
- Set `Context.allianceColor` on the dashboard before INIT (modules and paths read it then), never from an OpMode. With the dashboard off, as at events, it stays RED, so a blue match runs as RED (`docs/game-findings.md`).

**Ball routing**

- The planner doesn't map alliances: pass mapped coordinates, `BioBuzzField.ownHalf(margin)` as the area and, on the field, `BioBuzzField.hiveRails()` as the only obstacles.
- Plan with `RouteOptimizer.search(...)`, then one `Search.step()` per loop until it returns true, never a whole search in one loop: a 4-ball search takes seconds on a hub, and STOP waits for the running loop (past 900 ms the SDK restarts the app). A step runs `VisibilityGraphPlanner.routeSearchSliceMs` plus at most one `shape()`. A changed request is a new Search.
- Collections plan 4 balls (`BallCollection.BALLS`; Ball Collection plans its four slots): the order search is n!, and 5 balls take up to 15 s on a hub.
- Drive a plan only with `RouteRun`: `Plan.intake`/`Plan.back` are for drawing. They join the drives without the plan's turns in place, and Pedro moves to a compound path's next piece as soon as it would start braking (`ForesightConfig.pathSkip`, on by default), cutting reversals.

**Photon** (`architecture/hardware/photon/`, the team's fork of SolversLib Photon): only an OpMode annotated `@Photon` gets its hubs swapped for `PhotonLynxModule`s at INIT, and they stay swapped until the hardware map is rebuilt (config change or Restart Robot). `PhotonCore.enable()` throws unless that swap worked; it then sends RUN_WITHOUT_ENCODER `setPower` and servo pulse-width writes without waiting for each ACK, from any thread, on hubs with their own USB link. An RS485 Expansion Hub, and every command while disabled, takes the SDK's path. Every class there, nested ones included, must be `@Pinned`, with no lambdas or anonymous classes: an unpinned one is reloaded by deploySloth with its own copy of the statics. `@Photon` isn't inherited: a Photon variant of an OpMode is a subclass annotated `@Photon` (`FrameworkLoopPhotonBench`). `setMaxParallelWrites` takes 1 to 64. Don't send commands through a replaced hub object (an I2C client built on one shares its I2C lock, but a reply to a message number both objects hold is dropped and counted as `numberClashes`, and both commands time out). `PhotonCore.setWriteProfiling(true)` times every step of each parallel write, read per hub with `writeProfile(hub)`: bench use only. Status and bench: `docs/photon-bench.md`.

**Faults** (`architecture/core/Faults`) show only in an `EnhancedOpMode`, and on the Driver Station only while `OptimizationToggles.dsTelemetry` is on (`docs/framework-findings.md`); a bare `OpMode` shows the problem itself.

**OctoQuad localizer**: give a follower `GuardedOctoQuadLocalizer` (`architecture/hardware/`, built by `BioBuzzConstants.localizer`), never Pedro's `OctoQuadLocalizer` (hangs INIT, keeps stale poses); it faults in INIT and `EnhancedOpMode`'s START throws; a bare OpMode calls `awaitRunning()` (`docs/hub-bench-findings.md`).

**Game code.** Game commands go in `RobotActions` (`robot.actions`). `Camera` starts ENABLED, polling the Limelight and able to raise its fault, so an OpMode that doesn't use ball vision calls `disableBallVision()` in `initialize()`.

**Ball collection** (`RobotActions.collectBalls`) plans once and drives back to where it planned from. It ends SKIPPED on a Limelight fault before it plans, or on a START before the INIT Limelight sync is done (about 2 s; it waits only `visionWaitMs`).

**Vision** (`biobuzz/modules/vision/`): `Camera.getFieldBalls()` keeps a ball out of view for `forgetAfterSeconds`, frozen where last seen with `visible()` false: check `visible()` before chasing one.

**Ball detection** (`limelight/`) ships as the generated `LimelightFiles`, so deploySloth carries edits. After a lens recalibration, update `LENS_*` in both the SnapScript and `HomographyCalculationPipeline`.

**Limelight faults.** A failed sync isn't retried and nothing switches the Limelight back mid-OpMode: after a failed INIT sync, or with the Limelight left on another pipeline (e.g. a web-UI switch), re-INIT.

**Cell tip** (`CellTipCamera`): mount the webcam image-upright, facing the launch direction (an upright tag shows roll ≈ 0 on the stream overlay). Turn it off with `VisionState.DISABLED`, never `stop()`: that closes the webcam for good.

## OpMode lifecycle

A Module is read, written and stopped only if a field reachable from the OpMode or `robot` holds it by the end of `initialize()`; a Module's own fields aren't searched.

In INIT the follower and Ivy scheduler run but module writes don't (unless `shouldWriteDuringInit()`). Schedule commands from `onStart()` on: START drops earlier ones without `end()`, and a path command scheduled earlier drives the robot in INIT and keeps driving after START.

- Never call `telemetry.update()` in an `EnhancedOpMode`: it closes the DS frame and later DS lines are dropped.
- On `stop()` or a throwing hook, every Module whose `initStates()` began gets `stop()`, half-initialized ones included; `onEnd()` runs only on a normal stop.
- Keep `OptimizationToggles.dashboardTransmissionIntervalMs` low and `loopProfile` on: the team tunes on the dashboard.

## Module pattern

- Name every `@Config` in spaced words, a test OpMode's exactly as the OpMode: slothboard keys groups by that name (a bare `@Config` by its class's simple name), and a duplicate hides one group.
- Safe state lives in `stop()`, never only in a command's `end()`, which doesn't run at OpMode stop; stop motors with `EnhancedMotor.stop()`, since the write cache can drop `setPower(0)`.
- Keep `WriteCache`'s periodic re-send of an unchanged value, and add one to any new write cache: a hub reset or NACK drops a write silently.
- `stop()` can only de-energize: on a normal STOP the SDK has already fail-safed the hubs and silently drops any move, so stow a mechanism at the end of its routine.
- A State setpoint follows the dashboard only through `bindTunable(state, () -> Tuning.x)`; `Tuning.x` passed to the enum constructor is read once, and `setStates()` resets every variant, undoing a `setValue` made in a Module's constructor. A value set in `gameLoop()` or by a command reaches `write()` a loop late, since tunables refresh just before `read()` (`docs/framework-findings.md`).
- A failed hub read (bulk, ADC or I2C) returns zeros, 0.0 V for the battery, without throwing: guard anything that divides by a reading or acts on a sudden zero (`docs/sdk-hub-findings.md`).

## Commands

- Never call `Scheduler.execute()` or `Scheduler.reset()` in an `EnhancedOpMode`, which does both; a bare OpMode must do both itself, `reset()` at INIT.
- Build commands in `initialize()` or later: `StateCommands.set` takes each state's module when built, which in an OpMode field initializer may still be the previous OpMode's, so the command conflicts with nothing.
- A group holds all its children's requirements for its whole run, and a new command interrupts any colliding one of equal or lower priority: a `StateCommands.set` from `gameLoop()` on any module an auto touches kills the whole auto. Build reactions into the sequence, or give the auto `.setPriority(1)` and the reaction `.setBlockedBehavior(BlockedBehavior.QUEUE)`, which runs it after the auto.
- `PathCommands.remainingBelow` measures the current leg only, and reads the previous path's distance until the follower has updated on the new one, so with a follow scheduled from `gameLoop()` it can fire at once.
- Ivy's `Commands.waitMs` runs on the wall clock, which jumps decades the first time a DS or the RC web page connects after boot: use `PathCommands.waitMs`.
- Ivy's `PedroCommands.hold(f)` holds the pose read when the command is built (the INIT pose in a sequence built in `initialize()`): pass the pose, `PathCommands.hold(f, pose)` (`docs/pedro-findings.md`).
- Race every auto against `PathCommands.waitMs`: `PathCommands.timeout`, or a hand-built `race` to know whether it fired. Reference autos: `opmodes/test/MockAuto`, and `opmodes/test/auto/CloseFlowerAuto` on real paths.

Back to I2C: INIT and stop that OpMode with the sensor unplugged, then plug it in (LED turns magenta). Laser Rangefinder Test and Transfer Thread Count Test default to `biobuzz.xml`'s names (`frontRangefinder`, `backRangefinder`, `transfer`).
- **Color rangefinder** (Brushland, `vendor/brushland/ColorRangefinder`): configure it over I2C with Configure Color Rangefinder on `laser_rangefinder_i2c.xml` (`deviceName` is the config's device, `Laser` there). INIT shows what START will write; START writes both pins at once, since one pin left on I2C reverts the sensor to I2C. `pin0` DISTANCE (default) or HUE puts that channel on analog; NECTAR makes pin 0 digital, true for a hue in the red or blue range with something within `presenceMm`; pin 1 is always digital, true when something is within `presenceMm`. A hue range whose low is above its high wraps through 0 (written as two thresholds). `ledBrightness` -1 leaves the LED alone: the vendor page gives 0-100 in prose and 0-255 in its code. In HUE mode pin 1 is the sensor's digital "something within `presenceMm`"; plugged straight into an analog connector it should show on the connector's other channel as about 0 V or 3.3 V (inferred from the pages, not yet seen on a hub). Transfer Thread Count Test reads that channel as `presenceSensorName` (default `backRangefinder`, analog 3; once laser B, the rear entrance laser, is plugged into analog 3, point it elsewhere), shows it as `Ball present`, and with `usePresence` on reports no colour unless something is present. With pin 0 configured as DISTANCE instead, the same input is a distance, shown as `Colour sensor distance (mm), pin 0 in DISTANCE mode` (0 to 100 mm), and `Hue (deg)` then means nothing. The hue ranges are set around one reading of each ball on 2026-11-14 (red 30°, blue 190°, pollen 86°; an empty chute read 93°, only 7° from pollen: `docs/parts-findings.md`), so re-measure at the real mount before trusting NECTAR or a pollen reading. Afterwards plug it into Control Hub analog connector 2-3 (`colorRangefinder` is analog 2) with any side switch flipped away from the connector. Which hub channel pin 0 reaches is undocumented: if `Hue (deg)` sits at about 0 (`Ball colour` no signal), or only jumps between about 0 and 360 as something comes within `presenceMm` (likely pin 1's digital output, an inference), read `backRangefinder` (analog 3, same connector) instead, with the laser rangefinder unplugged. A digital output needs a digital port and a Digital Device in the config (`biobuzz.xml` has none); pin 1 beside an analog pin 0 needs a splitter cable. Back to I2C: INIT and stop Configure Color Rangefinder with the sensor unplugged, then plug it in (LED blinks). Vendor facts and gaps: `docs/parts-findings.md`.
- **Transfer Thread Count Test**: `frontRangefinder` (A) sits upstream of `backRangefinder` (B), close enough that one ball covers both; balls must only travel A to B and start with the chute clear. `motor1Power` runs the transfer motor and the `melonbotics` servo together, `intakePower` runs the intake (reversed by default, as in BioBuzz Basic Tele, so positive pulls balls in), and all three stop at `stopAtCount`. Gamepad 1 drives as in BioBuzz Basic Tele, with that OpMode's `drive` settings, and keeps driving after the count stops the rest. With one rangefinder, turn `oneSensor` on: it counts on the upstream sensor alone, each time its distance rises above `oneSensorThresholdMm` (set it halfway between the ball and empty-chute readings), and can't tell which way a ball moved; point `upstreamSensorName` at the port the sensor is in before INIT. To count in the loop only, with no thread and no hysteresis at a 20 ms loop: `runThread` off before INIT (it is read only there), `hysteresisMm` 0, `loopMs` 20, and read `Count (loop)` (an edge between START and the first loop is never counted, a `diffThresholdMm` change takes effect one sample later, and each loop also reads `motor1`'s encoder). It asks for `colorSensorName` at INIT (the color rangefinder in HUE mode; the active config must have it) and shows `Hue (deg)` and `Ball colour` each loop: no signal below `noSignalBelowDeg` (0 V is what a dead input reads, and it would otherwise count as red; a real red that low also reads no signal, so set it to 0 once the wiring is proven), else nectar red, nectar blue or pollen from the `*HueLowDeg`/`*HueHighDeg` ranges (checked in that order; low above high wraps through 0; a full-scale 360 is outside a range starting at 0), else none, background included. Each counted ball (the count that stops the motors) is tallied by the colour of the loop that sees the count, into `Nectar count`, `Pollen count`, `Other count` (none and no signal) and `Last ball colour`; `resetCount` zeroes them. That tally means something only if the colour sensor is looking at the ball at the moment the rangefinder count happens, which depends on where it is mounted; with the thread on, the colour is read up to one loop after the thread counts. The colour read adds one analog read to each loop's work. It also times the balls from the counter's own samples (the thread's `pollMs` polls, 10 ms by default, or each loop with `runThread` off): `Ball-to-ball period` last, shortest and mean, the periods since `resetCount` and the last 8. `resetCount` clears them, and so does changing `oneSensor`, a threshold or `hysteresisMm`, which don't reset the count and can themselves count a ball, so flip `resetCount` after one; the first ball after either gives no period. With `oneSensor` on it also shows `Ball in front of the beam` and `Gap between balls at the beam`; with two sensors, the time from a ball leaving A until it clears B or the next ball reaches A, and the rest of the period. Each is good to about one rangefinder update (20 ms at the default budget) or one poll or loop, whichever is longer, so for the five-ball speed test set a 10 ms budget and read the mean (`docs/transfer-findings.md`). `motor RPM` divides raw counts by goBILDA's 145.1 per output turn: `biobuzz.xml` declares `transfer` and `intake` as `goBILDA5202SeriesMotor`, the SDK's 2786-count 99.5:1 type, so `getMotorType()`, `getVelocity(AngleUnit)` and `RUN_USING_ENCODER` are wrong on both (`docs/parts-findings.md`).
- **Hub-reading threads** (reference: `biobuzz/modules/TransferCounter`): poll at 10 ms, the hub's ADC refresh; faster only costs loop time (`docs/hub-bench-findings.md`). Any such thread:
  - Call `start()` on the OpMode thread and `stop()` from the OpMode's stop, not `Module.stop()`, which also runs mid-OpMode.
  - Loop only while the OpMode thread `isAlive()`: after a crash the SDK calls no OpMode hook, so that is the only stop signal.
  - Stop with a volatile flag and `join`, never `interrupt()`: the SDK's `MessageKeyedLock.release` calls `lockInterruptibly()`, so an interrupt mid-command can leave the hub's USB lock held until it's abandoned after 500 ms, stalling every thread's hub commands (`docs/sdk-hub-findings.md`).
  - Catch `Throwable` into a volatile field and rethrow it on the OpMode thread.
  - Read with its own `LynxGetBulkInputDataCommand`, never through `AnalogInput` or `clearBulkCache()`: the MANUAL bulk cache is shared across threads.
  - No writes or telemetry from the thread.
- **Flywheel RPM** from a Through Bore: the hub's 16-bit velocity overflows above about 240 RPM at 8192 counts/rev, so compute it from position over a window (Intake Transfer Shooter Test's `rpmWindowMs`). Put the flywheel motor on port 0 or 3 with its Through Bore on the same-numbered encoder port, since it's read through the motor's port (two flywheels: 0 and 3 of one hub, or one per hub): ports 1 and 2 count in software and drop counts at that rate. Read `docs/flywheel-control-findings.md` before changing the flywheel loop, its RPM measurement or the shooter hardware.
- **Wiring the BIOBUZZ robot**: nothing that is read goes on the Expansion Hub (one input there adds its bulk read to every loop), outputs that change every loop go on the Control Hub, and `biobuzz.xml` follows the port map in `docs/wiring-findings.md`, which also lists the code the wiring needs: change the map and the config together. It names the Expansion Hub by USB serial, so another hub needs its serial there.
- Single devices: the dashboard's Hardware View.

**Control Hub bench** (`scripts/bench/`): read `docs/hub-bench-findings.md` before changing the planner, hub or I2C traffic, odometry, Limelight or stop paths.
- The bench's Pinpoint and OctoQuad settings are its own (`PinpointSetup`, `OctoQuadSetup` in `opmodes/test/bench/`), not the robot's: never point a bench at `BioBuzzConstants.octoQuad` or the robot's at the bench's.
- A bench gets a follower only from `BenchRobot` (`DrivingBenchGateTest` scans for any other): `benchFollower` (a real localizer, as `PinpointSetup.create`/`OctoQuadSetup.create` use) and `drivingFollower` refuse any config but the bench runner's and cap the wheels at 0.2; `softwareFollower` isn't gated, so a bench that lets Pedro drive never takes it.
- A new bench goes in its own file in `scripts/bench/benches/`, listed in its `order.txt`; extend a bench already in `run_bench.py` in place (`scripts/bench/benches/README.md`).
- **Photon block** (`run_bench.py --photon`): only a SAFE TO TRY ON THE ROBOT verdict from the go run for the robot's wiring clears Photon for the robot; how to run each block and what it needs: `docs/photon-bench.md`. Bench: Photon Stop's and Bench: Photon Stop Linear's negative controls deliberately breach STOP's gate, Bench: Photon Stop Race raises it mid-write and leaves it raised until the next INIT, and Bench: Photon's I2C negative control skips the hub's I2C lock: run them only through the runner, with the bench ports empty.
- A goBILDA 5202 motor is CCW, so its hub register holds minus the commanded power: compare register read-backs through `PhotonChannel.motorRegister`.
- `--dashboard-off` switches the hub's dashboard off on purpose and turns it back on over adb at the end; if that fails, the hub stays off until the command the runner prints is run. Keep it out of the default run and `--all`.
- **Session** (`scripts/bench/session.py`): one start runs every unattended stage and puts the hub back. Prompted benches never go in it: a new runner prompt goes in its `PROMPTED` list (`offline/test_session.py` fails until it does).

## Conventions

- An SDK bump sets `versionCode`/`versionName` to that SDK's FtcRobotController manifest values, then rechecks `docs/sdk-hub-findings.md` and the dashboard-gamepad check in `docs/dashboard-findings.md` (What the team build fixes over stock).
- Comments: none by default, in any language; only a one-line WHY a competent reader would otherwise get wrong. Usage notes go in this file.
- Vendored, never hand-edited, never holding tuned values (those go in `BioBuzzConstants`): `vendor/<source>/` (its `*_REV` names upstream and the only edits), `pedro/procedures/`, `robotcontroller/` and every `res/` file but the hardware configs. Refresh Prism and the procedures with `scripts/update-*.sh`, one commit each; the procedures' commit also carries any Pedro version bump the Quickstart made, in `TeamCode/build.gradle` (the script doesn't touch it); `robotcontroller/` and `res/` from the SDK's FtcRobotController at its tag; the rest by recopying upstream and reapplying its `*_REV` edits.
- Fail fast: no catch to keep a loop alive, no silent fallback, no optional devices (`hardwareMap.get`, never `tryGet`); numeric guards and try/finally are fine. Only exceptions: a webcam setting the camera rejects raises the `Webcam` fault and a Limelight problem the `Limelight` fault instead of throwing, with Limelight-dependent actions falling back; `GuardedOctoQuadLocalizer` raises the `OctoQuad` fault in INIT (START still throws); a Photon swap failure at INIT (then `PhotonCore.enable()` throws) or a dead Photon sweeper raises a global warning and leaves writes on the SDK's path.
- `Limelight3A` (`docs/limelight-findings.md`):
  - Every `boolean` call but `isRunning`/`isConnected` is an HTTP POST or DELETE that blocks up to 15 s and fails as a bare `false`: make them only from `LimelightSync`'s one background thread (newest request wins), and only when what's wanted changes.
  - `LLResult.getPipelineType()` is always empty (use `getStatus()`); llpython keeps the last script's output on every pipeline.
  - Poll errors are swallowed: health is `isConnected()`, `getTimeSinceLastUpdate()` and the result's contents.
  - `setPollRateHz` is ignored while polling: `stop()` first (`pause()` isn't enough). The rate persists across OpModes until the next deploySloth or app restart.
- OpModes always set `name`; `group` is exactly `"Test"`, or `"A"` for the competition TeleOp.
- Commits: one imperative subject line, no body, no trailer. Ask before pushing.
